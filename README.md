# Мастер-бот (master_bot)

**Сервис приёма входящих заявок на проекты для команды аккаунт-менеджеров.**

Заявки приходят с лендинга и через ботов в мессенджерах (Telegram, Яндекс 360),
каждая уходит на ИИ-оценку в отдельный Python-сервис через очередь NATS
JetStream и публикуется в чат менеджеров вместе с рекомендацией.

## Python-оценщик

Исходники команды DS подключены как Git-сабмодуль на коммите `b76cbd1`.
У них нет конфигурации для установки Python-пакета, поэтому образ берёт
исходники из сабмодуля и устанавливает зависимости из его `requirements.txt`.

```bash
git submodule update --init --recursive
cp -n .env.example .env
docker compose up --build --wait evaluator
curl http://localhost:8000/healthz
# {"status":"ok"}
```

При необходимости укажите `KODIK_API_KEY` в локальном `.env`. Compose передаёт
его только контейнеру оценщика. Для проверки `/healthz` ключ не требуется.

Чтобы запустить проверки локально, активируйте виртуальное окружение
с Python 3.12 и выполните из корня репозитория:

```bash
cd evaluator
python -m pip install -r vendor/brief-evaluator/requirements.txt '.[dev]'
python -m ruff check
python -m pytest
```

### Миграция базы данных V1

Подготовлена начальная миграция `V1__init_schema.sql` для PostgreSQL с использованием Flyway.

Миграция создаёт последовательность `application_number_seq` и следующие таблицы:

- `applications` — заявки и данные брифа;
- `application_status_history` — историю статусов заявок;
- `dialog_states` — состояния диалогов;
- `channel_inbox` — входящие события каналов с защитой от повторной обработки;
- `channel_cursor` — позицию последнего полученного обновления по каждому каналу;
- `outbox` — очередь исходящих сообщений (Transactional Outbox);
- `evaluation_jobs` — очередь фоновых задач оценки заявок;
- `evaluation_results` — результаты оценки заявок (связь один к одному с `evaluation_jobs`);
- `intake_idempotency` — защиту от повторной обработки запросов на создание заявок.

Добавлены внешние ключи, ограничения целостности (`CHECK`, `UNIQUE`, `PRIMARY KEY`),
индексы (включая частичные и уникальный частичный индекс на активные задания оценки),
последовательность номеров заявок, а также комментарии к таблицам и колонкам.

Для `evaluation_jobs` предусмотрены блокировки задач (`locked_at`, `locked_by`),
ограничение числа попыток (`max_attempts`, `attempts <= max_attempts`),
повторные запуски через `next_attempt_at` и статус `RETRY`, а также восстановление зависших задач
с использованием частичного индекса `idx_evaluation_jobs_running_locked_at` по `locked_at`
для записей в статусе `RUNNING`.

### Стэйт-машина заявок

- **`ApplicationStatus`** — enum с `canTransitionTo(target)` и `isTerminal()`;
  таблица переходов (`NEW → IN_REVIEW → ACCEPTED | REJECTED`) хранится в одном
  месте — `ALLOWED_TRANSITIONS`.
- **`Application`** — иммутабельный record-агрегат с каноническим конструктором (валидация инвариантов: `id`,
  `source`, `status` не `null`; `number > 0`;
  `version >= 0`; `history` копируется через `List.copyOf`) и фабриками
  `create(id, number, source)` / `restore(id, number, source, status, version, history)`;
  `changeStatus` возвращает новый экземпляр, увеличивая `version` и дополняя `history`.
- **`StatusChange`** — record-факт перехода: `from`, `to`, `actor`, `comment`, `at`. **`actor` обязателен для
  каждой смены статуса** (не только для терминальных) и
  проверяется в каноническом конструкторе `StatusChange` (`null`/`blank` → `IllegalArgumentException`).
- **`IllegalStatusTransitionException`** — доменное исключение при запрещённом переходе.
- **Тесты** — все 16 пар статусов покрыты `@CsvSource`; проверены терминальность, валидация,
- иммутабельность истории и обязательность `actor`.
- Тесты расположены в пакете `ru.yandex.masterbot.domain`.
- **Зависимости** — только `java.*`; ни Spring, ни JPA, ни Lombok.

**Сводная таблица перехода статусов**

| From \ To     | NEW | IN_REVIEW | ACCEPTED | REJECTED |
|---------------|-----|-----------|----------|----------|
| **NEW**       | ❌  | ✅        | ❌       | ❌       |
| **IN_REVIEW** | ❌  | ❌        | ✅       | ✅       |
| **ACCEPTED**  | ❌  | ❌        | ❌       | ❌       |
| **REJECTED**  | ❌  | ❌        | ❌       | ❌       |

## Сервис заявок и persistence-слой (DBA-02)

### ApplicationService

Реализован единый сервис `ApplicationService`, отвечающий за создание заявок и изменение их статусов. Сервис используется как единая точка входа для дальнейшей интеграции с HTTP API, ботом и другими каналами поступления заявок.

- `create(brief, source, requester)` — создание заявки.
- `transition(id, target, actor, comment)` — изменение статуса заявки.

### JPA и PostgreSQL

- `ApplicationEntity` — JPA-сущность заявки, соответствующая таблице `applications`.
- `StatusHistoryEntity` — JPA-сущность истории статусов, соответствующая таблице `application_status_history`.
- `ApplicationJpaRepository` и `StatusHistoryJpaRepository` — репозитории Spring Data JPA.
- Номер заявки генерируется PostgreSQL sequence `application_number_seq`.
- JSONB-поля отображаются через Hibernate `@JdbcTypeCode(SqlTypes.JSON)`.
- Hibernate работает в режиме `ddl-auto: validate`; структура БД определяется Flyway-миграциями.

### Архитектура

Используется разделение на application-слой и persistence-адаптер:

- `ApplicationStore` — порт хранения заявок, определённый в application-слое.
- `ApplicationStoreAdapter` — реализация порта на базе Spring Data JPA.
- `ApplicationMapper` — преобразование JPA-сущностей в доменную модель и обратно.
- `ApplicationQuery` — порт для получения последних заявок по requester.
- `ApplicationQueryAdapter` — реализация запросов к PostgreSQL.

ApplicationService не зависит напрямую от JPA, Entity или Spring Data Repository. Работа с persistence осуществляется через порт `ApplicationStore`.

### Транзакционность и конкурентный доступ

- Создание заявки выполняется с сохранением данных брифа, источника и requester.
- Смена статуса и запись в `application_status_history` выполняются в одной транзакции.
- Допустимость перехода проверяется доменной моделью `Application` / `ApplicationStatus`.
- Для обнаружения конкурентных изменений используется optimistic locking через `@Version`.
- При параллельном изменении одной заявки конфликт версий предотвращает успешное сохранение обоих переходов.

### Интеграционные тесты

`ApplicationServiceIntegrationTest` использует `SpringBootTest` и PostgreSQL через Testcontainers.

Проверяются сценарии:

- создание заявки и получение сгенерированного номера;
- успешная смена статуса и запись истории;
- недопустимый переход без изменения состояния заявки;
- конкурентные переходы одной заявки: один успешно завершается, второй получает ошибку optimistic locking;
- корректность итогового статуса, версии и истории после конкурентной операции.

### Безопасность API

Реализована схема с двумя независимыми Bearer-токенами и разделением доступа по путям.

#### Архитектура

Три цепочки фильтров Spring Security с явным порядком:

| Порядок     | Цепочка              | Matcher             | Назначение                                       |
|-------------|----------------------|---------------------|--------------------------------------------------|
| `@Order(1)` | `intakeFilterChain`  | `/api/v1/intake/**` | Публичный приём заявок с лендинга                |
| `@Order(2)` | `adminFilterChain`   | `/api/v1/**`        | Административные операции                        |
| `@Order(3)` | `defaultFilterChain` | `/**`               | Всё остальное: `denyAll`, кроме health и Swagger |

Ключевое свойство: каждая цепочка содержит **только свой фильтр**.
Intake-токен физически не может пройти admin-цепочку, и наоборот — «чужой» токен отвергается ещё до проверки
прав.

#### Токены

| Токен  | Свойство           | Роль          | Доступ                                       |
|--------|--------------------|---------------|----------------------------------------------|
| Admin  | `app.admin.token`  | `ROLE_ADMIN`  | Все `/api/v1/**`, кроме `/api/v1/intake/**`  |
| Intake | `app.intake.token` | `ROLE_INTAKE` | Только `/api/v1/intake/**` (создание заявок) |

Сравнение токенов — `MessageDigest.isEqual` (постоянное время), защита от timing-атак.
Токены валидируются в конструкторе фильтра: пустое или отсутствующее значение — `IllegalStateException`
на старте (fail-fast).

Утечка intake-токена позволяет **только создавать заявки**, но не читать их: в `IntakeController`
нет ни одного `GET`-эндпоинта, а admin-цепочка не принимает intake-токен.

#### Обработка ошибок

`401 Unauthorized` возвращается в формате `ProblemDetail` (`application/problem+json`)
через кастомный `AuthenticationEntryPoint`:

```json
{
  "title": "Unauthorized",
  "status": 401,
  "detail": "Authentication required"
}
```

Без подробностей о причине — чтобы не подсказывать атакующему, какой именно токен ожидался.

#### Открытые пути

- `/actuator/health/**` — health-check
- `/swagger-ui/**`, `/v3/api-docs/**` — OpenAPI-документация
- `OPTIONS /**` для intake-цепочки — CORS preflight

Всё остальное вне `/api/v1/**` — `denyAll` (`403`).

### Интеграция с Yandex Messenger Bot API

Реализован HTTP-клиент для взаимодействия с API Яндекс Мессенджера на базе Spring Boot 3.x и `RestClient`.

#### Реализованные возможности

- **Получение обновлений (`getUpdates`)**
  - Получение сообщений и других обновлений от API.
  - Поддержка параметров `offset` и `limit`.
  - Валидация входных параметров (`offset >= 0`, `1 <= limit <= 1000`).

- **Отправка текстовых сообщений (`sendText`)**
  - Отправка сообщений в указанный чат.
  - Передача данных в формате JSON.
  - Поддержка идентификатора чата (`chat_id`) и текста сообщения.

#### Архитектура и реализация

- Используется Spring `RestClient` для выполнения HTTP-запросов.
- Конфигурация приходит через ConfigurationProperties в 
[YandexProperties.java](src/main/java/ru/yandex/masterbot/adapter/yandex360/properties/YandexProperties.java)
- Настроена авторизация через заголовок `Authorization: OAuth <token>`.
- Реализованы DTO для запросов и ответов API:
  - `SendTextRequest`
  - `SendTextResponse`
  - `UpdatesResponse`
  - `YandexUpdate`
  - `YandexChat`
  - `YandexUser`
- Для преобразования JSON используется Jackson `ObjectMapper`.
- Добавлена обработка HTTP-ошибок с извлечением описания ошибки из ответа API.
- Реализована проверка поля `ok` для обработки ошибок, возвращаемых API с HTTP-статусом 200.
- Добавлено собственное исключение `YandexApiException` для унифицированной обработки ошибок.
- DTO и методы клиента документированы с помощью JavaDoc.


### Тестирование

- **Flyway**: миграции БД управляются через Flyway.
- **JUnit 5 + Spring Boot Test**: тесты используют Testcontainers.

#### Интеграционные тесты с Testcontainers

Настроена интеграционная тестовая среда на базе **Testcontainers**
с использованием PostgreSQL (`postgres:16-alpine`).

- Контейнер PostgreSQL запускается один раз на время работы тестового JVM.
- Подключение к PostgreSQL автоматически настраивается Spring через `@ServiceConnection`.
- Для тестов используется профиль `test`.
- Flyway включён: миграции выполняются при запуске тестового контекста.
- Hibernate работает в режиме `ddl-auto: validate`, проверяя соответствие JPA-сущностей реальной схеме БД.

Это позволяет запускать интеграционные тесты на PostgreSQL с той же схемой, что используется приложением,
без зависимости от локально установленной базы данных.

#### Тесты стейт-машины

Все 16 пар статусов покрыты `@CsvSource`; проверены терминальность, NPE,
иммутабельность истории, обязательность `actor`. Тесты лежат в том же пакете, что и продакшн-классы.

#### Тесты безопасности

Два уровня:

**`SecurityRoutingTest`** (`@WebMvcTest`) — быстрый срез, проверяет маршрутизацию цепочек и формат `401`:

- запрос без токена → `401` + `ProblemDetail`;
- intake-токен на admin-путь → `401`;
- admin-токен на intake-путь → `401`;
- открытые пути (Swagger, actuator) → не `401`;
- произвольный путь вне `/api/v1/**` → `403`.

**`TokenComparisonIntegrationTest`** (`@SpringBootTest` + Testcontainers) — интеграционный, проверяет реальное
сравнение `MessageDigest.isEqual` в полном контексте с PostgreSQL:

- admin-токен на admin-путь → security пройден;
- intake-токен на admin-путь → `401`;
- admin-токен на intake-путь → `401`;
- intake-токен на intake-путь → security пройден (контрольный тест, чтобы не сломать «пустить» в погоне за «не
  пустить»).

Инфраструктура — `AbstractIntegrationTest` с singleton-контейнером PostgreSQL 16 (Testcontainers,
`@ServiceConnection`), переиспользуемым между интеграционными тестами.

#### Тестирование Yandex Messenger Bot API

Реализованы интеграционные тесты с использованием WireMock:

- Проверка успешного получения обновлений.
- Проверка успешной отправки текстового сообщения.
- Проверка обработки HTTP-ошибок.
- Проверка обработки ответа API с `ok = false`.

Для тестовых HTTP-запросов используется HTTP/1.1 через `JdkClientHttpRequestFactory`, 
чтобы избежать проблем совместимости HTTP/2 с WireMock.
