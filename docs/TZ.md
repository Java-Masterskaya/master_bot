# ТЗ — master_bot (Java / Spring Boot)

Сервис приёма и первичной обработки входящих заявок на проекты для команды
аккаунт-менеджеров. Заявки приходят с **лендинга** и через **ботов в
мессенджерах**. Мессенджер подключается адаптером: первыми идут **Telegram** и
**Яндекс 360** (Телемост, бывший Яндекс Мессенджер), дальше любой другой без
изменений ядра. Каждая заявка сохраняется в Postgres, уходит на ИИ-оценку
(пайплайн команды DS, отдельный Python-сервис) через очередь **NATS
JetStream** и публикуется в чат аккаунт-менеджеров вместе с рекомендацией.
Менеджеры ведут заявки по статусам через REST admin API.

Задачи: [доска](https://github.com/orgs/Java-Masterskaya/projects/13),
issues #1–#43. Идентификаторы задач (`CON-01`, `TG-02` и т.д.) указаны в
разделах ТЗ, которые они реализуют.

---

## 1. Цель и контекст

Команда аккаунт-менеджеров разбирает входящие заявки с лендинга вручную:
читает каждую, решает, брать ли проект, пишет заказчику уточняющие вопросы.
Параллельно сотрудники (менеджеры, менторы, кураторы) заводят проекты от лица
заказчиков через Яндекс Форму, и заявка руками «падает на доску».

Нужен один сервис, который:
- принимает заявки с лендинга по HTTP;
- принимает заявки через бота в мессенджере (бот задаёт вопросы брифа по
  одному) — сейчас Telegram и Яндекс 360, позже любой другой;
- на каждую заявку запускает ИИ-оценку команды DS
  ([brief-evaluator](https://github.com/Al-brif-team1/brief-evaluator)):
  структура проекта, оценка задач, рекомендация
  (`accept/reject/clarify/simplify/expertise`), уточняющие вопросы и
  черновик ответа заказчику;
- постит заявку с оценкой в чат аккаунт-менеджеров;
- даёт admin API (под будущую админку), где аккаунт-менеджер берёт заявку
  в разбор, принимает или отклоняет.

Оценка — подсказка, решение по заявке принимает человек. Ответ внешнему
заказчику пишет аккаунт-менеджер сам (по черновику от ИИ), сервис письма не
шлёт.

**Каналы и кто через них приходит.**

| Канал | Кто | Ограничения |
|---|---|---|
| Лендинг (HTTP) | внешние заказчики | поля формы уточняются (§14) |
| Telegram | любые пользователи, в т.ч. внешние заказчики | нет ключа идемпотентности на отправке (§5.4) |
| Яндекс 360 | только сотрудники организации | бот не может писать людям вне своей организации Яндекс 360 |

Потребители:
- **Лендинг** — бэкенд формы на сайте, отправляет заявку в intake API.
- **Заявитель** — пользователь мессенджера, общается с ботом в личном чате,
  получает уведомления о статусе.
- **Чат аккаунт-менеджеров** — групповой чат в одном из мессенджеров
  (задаётся конфигом), куда бот постит новые заявки, оценки и смены
  статусов.
- **Аккаунт-менеджер** — ходит в admin API (Swagger UI/Postman/будущая
  админка).
- **Оценщик** — Python-сервис рядом, берёт задания из очереди.

## 2. Область

### В области
- Intake API для лендинга: отдельный токен, идемпотентность по
  `Idempotency-Key`, rate limit, сохранение сырого payload формы.
- **Ядро, не зависящее от мессенджера**: своя модель событий и сообщений,
  порты, реестр каналов (паттерны Adapter и Strategy, §4).
- **Адаптер Telegram**: long polling (`getUpdates`) по умолчанию, webhook —
  второй стратегией за флагом.
- **Адаптер Яндекс 360**: polling (`messages/getUpdates`).
- Общий цикл опроса для polling-адаптеров: курсор двигается только после
  фиксации обработки, дедупликация событий, один опрашивающий инстанс.
- Диалоговая FSM брифа, общая для всех мессенджеров: вопросы по одному,
  валидация, сводка, подтверждение кнопками, команды `/start`, `/отмена`,
  `/статус`. Состояние — в Postgres.
- Заявка со стейт-машиной `NEW → IN_REVIEW → ACCEPTED | REJECTED`.
- Уведомления заявителю и в чат аккаунт-менеджеров через **outbox** в
  Postgres.
- Admin API (REST, OpenAPI/Swagger UI): список с фильтрами и
  cursor-пагинацией, карточка, смена статуса, перезапуск оценки,
  статистика. Bearer-токен.
- **ИИ-оценка**: очередь NATS JetStream между Java и Python-оценщиком
  (FastAPI + воркер), гарантированная доставка заданий и результатов.
- Postgres + Flyway, NATS, docker compose, CI.

### Вне области
- Веб-UI админки (только API под неё).
- Сам лендинг, его форма и капча.
- Отправка ответов внешним заказчикам (email и т.п.).
- Адаптеры других мессенджеров (VK, MAX и т.д.) — архитектура их допускает,
  но в первую волну не входят.
- Webhook-режим Яндекс 360 (у платформы read timeout 1 с и нет подписи
  запросов) — после первой волны.
- Обучение и дообучение модели, изменение промптов и логики оценки — зона
  команды DS.
- Управление заявкой кнопками из чата аккаунт-менеджеров — кандидат на v2.
- Мультитенантность, пользователи и роли админки, OAuth, JWT.
- Редактирование брифа без деплоя, вложения в заявке.
- Интеграция с трекерами/досками, экспорт в Яндекс Формы.
- NLP: бот понимает только ответы на текущий вопрос, кнопки и команды.
- Автоматическая смена статуса по рекомендации ИИ и автоотправка черновика
  заказчику (кандидат на v2).
- Kafka (решение §11.3).

## 3. Стейт-машина заявки

`DOM-01`, `DB-02`, `API-04`

```
NEW ──> IN_REVIEW ──> ACCEPTED
              └─────> REJECTED
```

- Переходы только по стрелкам; правила — в domain-enum
  (`canTransitionTo`), не размазаны по сервисам.
- Смена статуса фиксируется в истории (актор, время, комментарий).
- `ACCEPTED`/`REJECTED` — терминальные.
- Переход — одна транзакция: статус + история + outbox-события
  (заявителю и в чат аккаунт-менеджеров).
- Конкурентные переходы одной заявки — оптимистическая блокировка
  (`@Version`), проигравший получает 409.

## 4. Архитектура: ядро и адаптеры мессенджеров

`CON-01`, `CH-01`

```
              ядро (domain + application)
   ┌────────────────────────────────────────────────┐
   │ BriefDialog (FSM)   ApplicationService  Outbox │
   └───────▲──────────────────────────────┬─────────┘
           │ IncomingEvent                │ OutgoingMessage
   ┌───────┴──────────────────────────────▼─────────┐
   │ порты: UpdateSource · MessengerSender ·        │
   │        MessengerCapabilities · SendErrorClassifier │
   └───────▲──────────────────▲─────────────────────┘
     TelegramAdapter     Yandex360Adapter     (…другие — потом)
```

### 4.1 Модель ядра

- `Channel` — `TELEGRAM`, `YANDEX360`.
- `ChannelUserRef{channel, userId, chatId, displayName}` — кто пишет боту.
- `IncomingEvent` (sealed) с общими полями `channel`, `updateId`, `from`:
  - `Text(text)` — ответ на вопрос;
  - `ButtonPress(actionId, payload)` — нажатие кнопки;
  - `Command(name, args)` — `/start`, `/отмена`, `/статус`;
  - `Unsupported(kind)` — файл, стикер и прочее.
- `OutgoingMessage{target, text, buttons, idempotencyKey}`, `Button{actionId,
  title, payload}`.

Ядро не импортирует ни одного класса Telegram, Яндекс 360 или NATS. Это
проверяет ArchUnit-тест (`INF-01`), а не договорённость.

### 4.2 Порты (Adapter)

Каждый мессенджер — пакет `adapter/<name>` с реализацией портов:

| Порт | Что делает |
|---|---|
| `UpdateSource` | `fetch(cursor) → Batch(events, nextCursor)`: забирает обновления мессенджера и переводит в `IncomingEvent` |
| `MessengerSender` | `send(OutgoingMessage)`: переводит сообщение ядра в API мессенджера |
| `MessengerCapabilities` | `maxTextLength`, `supportsButtons`, `supportsIdempotency`, экранирование текста под разметку |
| `SendErrorClassifier` | ошибка отправки → `TRANSIENT` (ретрай) или `PERMANENT` (`FAILED`) |

### 4.3 Где Strategy

Поведение, которое реально различается по каналу, вынесено в стратегии, а не
в `if (telegram)`:
- **получение обновлений** — polling или webhook, выбирается
  `channels.<name>.mode`;
- **возможности канала** — FSM режет сводку по `maxTextLength` и рисует
  кнопки или нумерованный список по `supportsButtons`;
- **классификация ошибок** — что ретраить, а что сразу `FAILED`.

### 4.4 Реестр каналов

`ChannelRegistry` собирает включённые в конфиге адаптеры
(`channels.telegram.enabled`, `channels.yandex360.enabled`) и отдаёт нужный
по `Channel`. Новый мессенджер = новый пакет `adapter/<name>` + блок в
конфиге; ядро не меняется.

## 5. Мессенджеры

### 5.1 Общий цикл опроса

`CH-02`, `CH-03`, `DLG-04`

- Поток на канал (`SmartLifecycle`, virtual thread), корректная остановка.
- Цикл:
  1. курсор из `channel_cursor` → `UpdateSource.fetch(cursor)`;
  2. каждое событие — в `DialogService.onEvent` в своей транзакции: вставка
     в `channel_inbox (channel, update_id)` `ON CONFLICT DO NOTHING` → шаг
     FSM → ответы в outbox;
  3. **только после** всей пачки сохраняется `nextCursor`.
- Падение между шагами 2 и 3 → пачка приходит снова, inbox отсеивает
  дубли.
- Почему так строго: у Яндекс 360 запрос с новым `offset` безвозвратно
  удаляет старые обновления на сервере, у Telegram — подтверждает их.
  Сдвинуть курсор раньше фиксации = потерять сообщения пользователей.
- Ошибка опроса → пауза с экспоненциальным backoff, цикл не умирает.
- Один опрашивающий инстанс на канал — Postgres advisory lock; остальные
  реплики работают как API.
- Health-индикатор по каналу: держит ли лок, время последнего успешного
  опроса.

### 5.2 Telegram

`TG-01`…`TG-04`. Документация: https://core.telegram.org/bots/api

- Тонкий клиент на `RestClient`: `getMe`, `getUpdates` (long polling,
  `timeout` 25 с, `allowed_updates=[message, callback_query]`),
  `sendMessage`, `answerCallbackQuery`.
- Курсор — `offset` = последний `update_id` + 1.
- Входящие: `message.text` → `Text`/`Command`; `callback_query` →
  `ButtonPress` и сразу `answerCallbackQuery` (иначе у пользователя
  «крутится» кнопка). Только `private`-чаты; группы — только как чат
  менеджеров.
- Кнопки — `inline_keyboard`. `callback_data` ограничен 64 байтами: в кнопку
  кладётся короткий токен, полный payload хранится в БД.
- Возможности: 4096 символов, кнопки есть, **идемпотентности отправки нет**.
- Ошибки: 429 → ждать `parameters.retry_after`; 5xx и таймаут —
  временные; 403 «bot was blocked by the user» — постоянная.
- Троттлинг: ~1 сообщение/с в один чат, ~30/с всего.
- Webhook (`TG-04`) — вторая стратегия `UpdateSource`: проверка заголовка
  `X-Telegram-Bot-Api-Secret-Token`, `setWebhook`/`deleteWebhook` при
  старте, быстрый ответ 200, обработка через тот же `DialogService`.

### 5.3 Яндекс 360 (Телемост)

`YA-01`…`YA-04`. Документация: https://yandex.ru/dev/messenger/doc/ru/

- Клиент на `RestClient`, `Authorization: OAuth <token>`, базовый URL
  `https://botapi.messenger.yandex.net/bot/v1`: `messages/getUpdates`
  (`limit` ≤ 1000), `messages/sendText`.
- Курсор — `offset` = max `update_id` + 1. Запрос с новым `offset` удаляет
  на сервере все обновления с меньшим `update_id` — двигает его только
  общий цикл (§5.1).
- Входящие: `text` в `private` → `Text`/`Command`;
  `bot_request.server_action` → `ButtonPress`; `from.robot = true` —
  игнор.
- Кнопки — `suggest_buttons` с директивой `server_action` (не устаревший
  `inline_keyboard`).
- Возможности: 6000 символов, кнопки есть, идемпотентность есть
  (`payload_id`).
- Постоянные ошибки: «Bot is not a member of the chat», пользователь вне
  организации, личка запрещена.
- Бота создаёт администратор организации в `admin.yandex.ru/bot-platform`;
  токен показывается один раз. Rate limit и окно дедупликации `payload_id`
  в документации не описаны — проверяются на живом боте (`YA-04`).

### 5.4 Защита от дублей при отправке

- Яндекс 360: `payload_id = idempotencyKey` — повтор отправки после таймаута
  не создаёт второе сообщение.
- Telegram: ключа идемпотентности у `sendMessage` нет. Если запрос
  отвалился по таймауту уже после фактической отправки, пользователь может
  изредка получить сообщение дважды. Данные в БД при этом не дублируются.
  Это задокументированное ограничение, не баг.

## 6. Сценарий брифа (диалог)

`DOM-02`, `DLG-01`…`DLG-04`

Пользователь пишет боту в личный чат что угодно или `/start` → бот
приветствует и ведёт по вопросам. Поля брифа:

| # | Поле | Валидация |
|---|------|-----------|
| 1 | Название проекта | 3–200 символов |
| 2 | Организация-заказчик | 2–200 символов |
| 3 | Описание: что за продукт, какую задачу решает | 30–3000 символов |
| 4 | Что должно получиться на выходе (MVP) | 10–2000 символов |
| 5 | Желаемый стек/ограничения | свободный текст, «нет» допустимо |
| 6 | Сроки/дедлайны | свободный текст |
| 7 | Контакт заказчика (почта/телеграм/телефон) | непустой |

Заявитель определяется из события (`ChannelUserRef`), отдельно его не
спрашиваем. Длина считается в символах Unicode, а не в `char`.

FSM — чистая функция `BriefDialog.handle(state, event, capabilities, clock)
→ (newState, messages)`, без Spring и БД.

Правила диалога:
- Один активный черновик на пользователя канала. `/start` при активном
  черновике — кнопки «Продолжить / Начать заново».
- Невалидный ответ → повтор вопроса с подсказкой, попытки не ограничены.
- Файл/стикер (`Unsupported`) → «нужен текстовый ответ».
- После последнего вопроса — сводка + кнопки «Отправить / Исправить /
  Отмена». «Исправить» — кнопки с номерами вопросов.
- Канал без кнопок → те же действия цифрами в тексте.
- Сводка длиннее `maxTextLength` канала → несколько сообщений по границам
  полей, кнопки под последним.
- Версия черновика в payload кнопки: нажатие со старого сообщения не меняет
  состояние, бот отвечает «черновик неактуален».
- «Отправить» → заявка `NEW`, бот отвечает номером заявки; карточка уходит
  в чат аккаунт-менеджеров, задание — на оценку.
- `/статус` → последние заявки этого пользователя; `/отмена` → черновик
  удаляется.
- Черновик без активности 72 часа протухает: следующее сообщение начинает
  новый бриф с предупреждением.
- На старте брифа бот предупреждает, что ответы обрабатываются
  автоматически, в т.ч. ИИ.

## 7. Уведомления и outbox

`OUT-01`, `OUT-02`

- Все исходящие эффекты пишутся в таблицу `outbox` в той же транзакции,
  что и бизнес-изменение (`OutboxWriter`, `Propagation.MANDATORY`).
- Релей — `@Scheduled`: батч `FOR UPDATE SKIP LOCKED` → обработчик по типу
  события (`OutboxHandler`):
  - `message` → адаптер из `ChannelRegistry`;
  - `evaluation.requested` → публикация в NATS (§8).
- Ошибка `TRANSIENT` → `attempts++`, `next_attempt_at` с backoff и jitter;
  `PERMANENT` → `FAILED` + `last_error`; лимит попыток.
- Что и кому:
  - заявителю — «заявка принята, №…», смены статуса с комментарием
    менеджера; только если у заявки есть заявитель (у лендинга нет);
  - в чат аккаунт-менеджеров — карточка новой заявки (номер, источник,
    название, заказчик, заявитель, описание до 500 символов, ссылка на
    карточку), смены статуса, готовая оценка (рекомендация, первые
    причины, число вопросов) — ответом в тред карточки, где канал это
    умеет.
- Чат аккаунт-менеджеров задаётся конфигом `managers-chat.{channel,
  chatId}` и может быть в любом подключённом мессенджере. Пусто —
  публикация выключена.
- Пользовательский текст экранируется под разметку канала
  (`MessengerCapabilities`).

## 8. ИИ-оценка брифа

### 8.1 Что передала команда DS

Архив с Яндекс Диска (`brief-evaluator-master.zip`) побайтно совпадает с
GitHub `Al-brif-team1/brief-evaluator`, коммит `b76cbd1` — его и фиксируем.
Внутри только LLM-пайплайн: 5 модулей, промпты, вызовы `openai/gpt-4o-mini`
через KodikRouter (`temperature=0`), Pydantic-схемы ответа. **Обученной
модели (весов, ноутбуков, кода обучения) в переданном нет** (§14 п.0).

Пайплайн уже отделяет инструкции от данных брифа тегом `<untrusted_data>`
(защита от prompt injection через текст заявки). Обёртка это сохраняет:
текст заявки попадает только в поля данных.

### 8.2 Транспорт: очередь NATS JetStream

`CON-02`, `EV-01`…`EV-03`, `PY-03`. Документация:
https://docs.nats.io/nats-concepts/jetstream

```
 Java (master_bot)                    NATS JetStream               Python (evaluator)
 ─────────────────                    ──────────────               ──────────────────
 tx: заявка + evaluation_jobs
     + outbox(evaluation.requested)
 outbox-релей ── publish ──────────▶  eval.requests.v1  ── pull ──▶ воркер: оценка
   Nats-Msg-Id = jobId                 (стрим EVAL, диск)            │
                                                                     ▼
 консьюмер results ◀── pull ───────  eval.results.v1  ◀─ publish ── результат
   дедуп по jobId, commit, ack                            Nats-Msg-Id = jobId,
                                                          потом ack задания
```

- Стрим `EVAL` (`eval.>`, хранение на диске, `duplicate_window` 10 мин).
- Durable-консьюмеры: `evaluator` (Python, `AckWait` 300 с, `MaxDeliver`
  3) и `results` (Java).
- Публикация со стороны Java — через outbox-релей, с ожиданием ack от
  JetStream и `Nats-Msg-Id = jobId` (повторная публикация в окне
  дедупликации не создаёт второе сообщение).
- Python подтверждает задание **только после** публикации результата.
  Падение посреди оценки → задание доставляется снова.
- Последняя попытка (`MaxDeliver`) неудачна → Python публикует результат
  `FAILED` с ошибкой.
- Java сохраняет результат с дедупликацией по `jobId` и подтверждает его
  после commit.
- Гарантия: at-least-once на каждом участке, один зафиксированный
  результат на задание. Оценщик может быть выключен сколько угодно —
  задания ждут в стриме, заявки принимаются.
- Сторож (`EV-04`): задание без результата дольше N минут → `FAILED`,
  видно в карточке.

### 8.3 Контракт сообщений

JSON со `schemaVersion`, схемы в `contracts/eval/` (`CON-02`), Java и Python
валидируют по одним схемам.

```
eval.requests.v1
  { schemaVersion, jobId, applicationId, text }

eval.results.v1
  { schemaVersion, jobId, status: DONE | FAILED,
    recommendation: accept | reject | clarify | simplify | expertise,
    finalReasons: [...], tasksAssessment: [{task, category, reason}],
    questions: [...], responseDraft, degraded, errors: [...],
    usage: {promptTokens, completionTokens},
    model, evaluatorVersion, durationMs }
```

### 8.4 Python-оценщик

`PY-01`…`PY-03`

- Каталог `evaluator/`: Python 3.12, FastAPI, отдельный образ и сервис в
  compose. Код DS — зависимость на коммите `b76cbd1`, не правим.
- `GET /healthz` — готов, когда подключён к NATS; `POST /v1/evaluations` —
  синхронная оценка для отладки, тот же код, что в воркере.
- Воркер в lifespan FastAPI, параллелизм из конфига (по умолчанию 1).
- Обёртка над пайплайном DS:
  - пропускает `TextExtractionModule` (читает `.docx` с диска) — текст
    приходит в задании;
  - счётчик токенов и замер времени — свои на каждое задание (в исходнике
    счётчик глобальный и копится между запусками);
  - ошибка модуля → `degraded: true` и `errors`, а не молчаливый
    `expertise`;
  - `print` → логи.
- `KODIK_API_KEY` — только в env оценщика.
- Если DS передаст отдельную обученную модель: веса не в git (volume или
  артефакт), загрузка один раз на старте, `/healthz` готов после загрузки,
  версия весов в `evaluatorVersion`. Тяжёлый инференс — оценщик на
  отдельной машине; меняется только адрес NATS. Java не меняется.

### 8.5 Сторона Java

`EV-02`…`EV-04`

- Создание заявки (бот или лендинг) в той же транзакции создаёт
  `evaluation_jobs` `PENDING` и outbox-событие `evaluation.requested`.
- Текст для оценки собирается из полей брифа 1–6 с заголовками; для
  лендинга — из смапленных полей формы. **Контакты заказчика и данные
  заявителя в оценку не отправляются.**
- `recommendation` вне enum → `expertise`; остальной ответ — недоверенный
  текст.
- Готовая оценка → outbox-событие в чат аккаунт-менеджеров.
- Флаг `evaluation.enabled=false` — задания не создаются, оценщик и стрим
  не нужны.

## 9. HTTP API

### 9.1 Admin API (`/api/v1`, admin-токен)

`CON-03`, `API-01`…`API-05`, `EV-04`

- `GET /applications` — фильтры `status`, `source`, `recommendation`,
  `createdFrom/To`, `q`; cursor-пагинация по `(created_at, id)`, `limit` ≤
  100, `nextCursor`.
- `GET /applications/{id}` — бриф, источник, заявитель, `raw_payload`,
  история статусов, блок `evaluation` (статус задания, рекомендация,
  причины, оценка задач, вопросы, черновик ответа, `degraded`, версия,
  токены).
- `POST /applications/{id}/transitions {status, comment}` — 422 на
  недопустимый переход, 409 на конфликт версий, повтор в тот же статус → 200
  без дублей в истории и outbox. Актор — заголовок `X-Actor` (до появления
  пользователей админки).
- `POST /applications/{id}/evaluations` — перезапуск оценки (новый `jobId`),
  409 если есть активное задание.
- `GET /stats` — по статусам и источникам, за 7/30 дней, медианное время до
  решения, распределение по рекомендациям, расход токенов.
- Health — `actuator`, без токена: БД, NATS, каналы.
- Ошибки — `ProblemDetail` (RFC 9457), валидация — `fieldErrors`.
- Документация — springdoc, Swagger UI.

### 9.2 Intake API для лендинга

`API-06`

- `POST /api/v1/intake/applications` — вызывает бэкенд лендинга. Отдельный
  `intake.token`: у лендинга нет прав читать и менять заявки.
- Обязательный `Idempotency-Key`: тот же ключ и тело → 200 с той же заявкой;
  тот же ключ и другое тело → 422; ключи хранятся 7 дней. Хэш — по
  канонизированному JSON.
- Известные поля → бриф; остальное → `raw_payload jsonb`. Минимум — описание
  ≥ 30 символов и хотя бы один контакт.
- Ответ `201 {id, number}`; заявка `NEW`, источник `LANDING`; карточка в
  чат и задание на оценку — в той же транзакции.
- Rate limit на токен → 429; тело ≤ 64 КБ.
- Если лендинг умеет только webhook конструктора (Tilda и т.п.) — адаптер
  под его формат с секретом в URL, после ответа по §14.

## 11. Нефункциональные требования и решения

### 11.1 Стек и структура

`INF-01`…`INF-04`

- Java 21, Spring Boot 3.x, Gradle (Kotlin DSL); Python 3.12 + FastAPI для
  оценщика.
- Пакеты: `domain`, `application`, `port`, `adapter/{http, persistence,
  telegram, yandex360, nats}`, `config`. ArchUnit: `domain` и
  `application` не импортируют `adapter`, `domain` не импортирует Spring.
- Spring Data JPA + Flyway; native query для `ON CONFLICT` и `SKIP LOCKED`.
- Клиенты внешних API — `RestClient` с таймаутами; NATS — `io.nats:jnats`,
  в Python — `nats-py`.
- JSON-логи, correlation-id, graceful shutdown.
- Конфиг: `@ConfigurationProperties` + `@Validated`; включённый канал без
  токена — сервис не стартует.
- `docker compose up` поднимает Postgres, NATS (`-js`, volume), сервис,
  оценщик. Стрим и консьюмеры создаются приложением, не руками.
- CI: `./gradlew check` (unit + Testcontainers Postgres и NATS), `pytest` и
  `ruff` для оценщика, сборка образов. В CI нет реальных токенов: внешние API
  — WireMock, LLM — фейк.

### 11.2 Тесты

- unit — стейт-машина, бриф, FSM (текст, кнопки, старые нажатия, канал без
  кнопок, длинная сводка, протухание);
- slice — `@WebMvcTest` на контроллеры и security;
- интеграционные (Testcontainers) — inbox-дедуп, курсор при падении,
  advisory lock, outbox, keyset-пагинация, идемпотентность intake, NATS:
  публикация, дедупликация, повторная доставка;
- адаптеры — WireMock (маппинг, кнопки, 403/429/5xx, постоянные ошибки);
- оценщик — pytest с фейковым LLM и NATS в testcontainers;
- сквозные (`E2E-01`, `E2E-02`) — живые Telegram и KodikRouter на
  `docker compose up`.

### 11.3 Решения

- **Adapter + Strategy для мессенджеров** — ядро не знает про конкретный
  мессенджер; новый канал = новый пакет и блок конфига. Различия каналов —
  в стратегиях, а не в `if`.
- **Telegram — первый адаптер** — пускает любых пользователей, поэтому это
  основной канал для внешних заказчиков; Яндекс 360 — для сотрудников и
  чата менеджеров.
- **Polling по умолчанию** — не нужен публичный HTTPS-адрес, проще
  разработка; webhook Telegram — стратегией за флагом.
- **Курсор двигается только после фиксации** — иначе теряются сообщения
  (§5.1).
- **NATS JetStream, не Kafka и не ZeroMQ.** Kafka — тяжёлая инфраструктура
  для одного продюсера и одного консьюмера. ZeroMQ — без брокера и
  хранения: оценщик лёг — сообщение потеряно, подтверждения и ретраи
  пришлось бы писать самим. JetStream — один лёгкий контейнер, хранение на
  диске, ack, повторная доставка и дедупликация публикации из коробки.
  Запасной вариант, если брокер не согласуют, — очередь в Postgres через
  `SKIP LOCKED`.
- **Outbox в Postgres для всех исходящих эффектов** — сообщения и задания не
  теряются при падении между commit и вызовом внешней системы.
- **Оценщик — отдельный Python-сервис, не порт на Java** — промпты и логику
  ведёт DS; порт разошёлся бы с их кодом после первой правки.
- **Оценка асинхронная** — пайплайн идёт десятки секунд (4 вызова LLM
  подряд); синхронный вызов держал бы пользователя и падал бы вместе с
  провайдером.
- **Оценка — подсказка, не решение** — статус меняет только менеджер.
- **Intake — отдельный эндпоинт и токен** — утечка токена лендинга позволяет
  только создавать заявки.
- **Статический bearer вместо JWT** — одна роль; появятся пользователи
  админки — заменим фильтр, контракт API не меняется.
- **Бриф в коде** — редактор форм раздул бы область втрое; поля в одном enum.

## 12. Безопасность

- Spring Security, stateless, deny-by-default; открыты health и Swagger.
- Разные секреты с разными правами: admin-токен, intake-токен, токены ботов
  (по одному на канал), `KODIK_API_KEY` (только у оценщика). Только из env,
  не логируются; токен Telegram стоит в URL запроса — логировать путь без
  него.
- Сравнение токенов — `MessageDigest.isEqual`; 401 без подробностей.
- Webhook Telegram — проверка `X-Telegram-Bot-Api-Secret-Token`.
- Intake торчит наружу: HTTPS на прокси, лимит тела, rate limit.
- Персональные данные (имена, почты, телефоны заказчиков) в логи не пишутся.
- Текст брифа уходит внешнему LLM-провайдеру (KodikRouter); контакты и
  данные заявителя — нет. Для лендинга согласие на обработку ИИ собирает
  форма (§14).
- Ответ LLM — недоверенные данные: только текст, кроме `recommendation`
  (валидация по enum).
- NATS — только во внутренней сети compose; для стенда — пользователь и
  пароль NATS из env.

## 13. Критерии приёмки (Definition of Done)

**Лендинг**
- [ ] `POST /api/v1/intake/applications` → 201 с номером, заявка `NEW`
      `LANDING`, карточка в чате менеджеров, через ≤ 3 мин — оценка.
- [ ] Повтор с тем же `Idempotency-Key` → та же заявка, без дубля в чате;
      тот же ключ с другим телом → 422.
- [ ] Intake-токен не открывает admin API и наоборот.

**Мессенджеры**
- [ ] Бриф целиком проходит в Telegram: 7 вопросов → сводка → «Отправить» →
      заявка, номер заявителю, карточка в чате менеджеров.
- [ ] То же в Яндекс 360 (после получения организации и токена).
- [ ] Ядро проходит тесты без единого реального адаптера (на
      `FakeMessenger`).
- [ ] Подключение второго адаптера не потребовало изменений в `domain` и
      `application` (проверяется ревью и ArchUnit).
- [ ] Переключение Telegram `polling ↔ webhook` — только конфигом.
- [ ] Повтор того же события не создаёт второй шаг и вторую заявку.
- [ ] Падение после обработки пачки, но до сохранения курсора, не теряет и
      не дублирует события.
- [ ] Старое нажатие «Отправить» не создаёт вторую заявку.
- [ ] Рестарт посреди брифа не теряет прогресс.
- [ ] Два инстанса — канал опрашивает один.

**Уведомления**
- [ ] Мессенджер недоступен → сообщение ждёт в outbox и уходит после
      восстановления; постоянная ошибка → `FAILED` без бесконечных ретраев.
- [ ] Смена статуса доводит сообщения до заявителя и в чат менеджеров;
      заявка без заявителя — только в чат.

**ИИ-оценка**
- [ ] Оценщик выключен → заявки принимаются, задания ждут в стриме, после
      включения доходят до результата.
- [ ] Падение оценщика посреди оценки → задание доставляется снова,
      результат один.
- [ ] Повторная доставка результата не создаёт второе сообщение в чате.
- [ ] В задании на оценку нет контактов заказчика и данных заявителя
      (тест на тело).
- [ ] Ошибка внутри пайплайна DS видна как `degraded: true`.
- [ ] Перезапуск оценки создаёт новое задание; при активном — 409.
- [ ] `evaluation.enabled=false` → сервис работает без оценщика и NATS.

**Admin API и инфраструктура**
- [ ] Список с курсором стабилен при вставке новых строк.
- [ ] Переход: 200 / 409 / 422 по правилам §3, повтор — без дублей.
- [ ] Без токена → 401; ошибки — `ProblemDetail`; Swagger описывает всё.
- [ ] `cp .env.example .env && docker compose up` → рабочий стенд с нуля.
- [ ] CI зелёный: `./gradlew check`, `pytest`, `ruff`.
